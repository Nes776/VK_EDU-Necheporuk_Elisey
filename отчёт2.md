## 1. Вариант и задача

| Поле | Значение |
|---|---|
| ФИО | Нечепорук Елисей Сергеевич |
| Тема | Вариант 1 — CDC → SCD → Lakehouse |
| Состав решения | PostgreSQL, Debezium, Kafka, Spark Structured Streaming, Apache Iceberg, MinIO, Lakekeeper, Trino |
| Тип задачи | Захват изменений операционного справочника и сохранение истории изменений |
| Данные | Справочник банковских счетов `public.accounts` |

### Постановка задачи

В рамках работы необходимо спроектировать архитектуру, которая позволяет отслеживать изменения в операционной базе данных PostgreSQL и сохранять историю этих изменений в аналитическом хранилище.

В качестве примера используется справочник банковских счетов. В процессе работы с ним могут изменяться владелец счёта, статус и баланс. При этом аналитикам и сотрудникам бухгалтерии важно иметь возможность получить не только актуальное состояние записи, но и узнать, какие значения были у неё в прошлом.

Например:
- кто являлся владельцем счёта на определённую дату;
- какой статус был у счёта до его изменения;
- как изменялся баланс;
- когда запись была создана, изменена или удалена.

Для решения задачи используется CDC (Change Data Capture) — механизм захвата изменений непосредственно из журнала транзакций PostgreSQL. Полученные события передаются через Kafka, обрабатываются Spark и сохраняются в Lakehouse в формате Apache Iceberg.

Основной подход к хранению истории — SCD Type 2.

## 2. Источники и способы сбора

В проекте используется один основной источник данных — PostgreSQL.

| Источник | Тип | Способ сбора | Назначение |
|---|---|---|---|
| PostgreSQL `public.accounts` | Операционная база данных | CDC через Debezium и WAL | Хранение текущего состояния счетов и регистрация изменений |
| Kafka | Поток событий | Получение сообщений от Debezium | Буферизация и передача изменений потребителю |
| Apache Iceberg | Аналитическое хранилище | Запись обработанных данных через Spark | Хранение исторических версий записей |

### PostgreSQL

PostgreSQL используется в качестве основной операционной базы данных. В ней находится таблица `public.accounts`, содержащая информацию о банковских счетах.

Основные поля таблицы:

| Поле | Тип | Описание |
|---|---|---|
| `account_id` | BIGSERIAL | Уникальный идентификатор счёта |
| `owner_name` | TEXT | Имя владельца |
| `status` | TEXT | Текущий статус счёта |
| `balance` | NUMERIC(14,2) | Баланс счёта |
| `updated_at` | TIMESTAMPTZ | Время последнего изменения |

PostgreSQL настроена для логической репликации с использованием `wal_level=logical`. Это позволяет Debezium получать информацию об изменениях из WAL (Write-Ahead Log).

Такой способ предпочтительнее постоянного выполнения SELECT-запросов, поскольку позволяет фиксировать изменения без необходимости регулярно сканировать всю таблицу.

### Debezium

Debezium используется для захвата изменений в PostgreSQL.

Для подключения применяется PostgreSQL Connector с плагином `pgoutput`. Коннектор отслеживает изменения таблицы `public.accounts` и преобразует их в события CDC.

В зависимости от операции формируются события:
- `c` — создание записи;
- `u` — обновление записи;
- `d` — удаление записи;
- `r` — запись, полученная в рамках начального снимка данных.

Каждое событие содержит информацию об изменении и данные записи до или после операции.

### Apache Kafka

Kafka используется как промежуточный слой между Debezium и Spark.

События изменений поступают в топик:

`dbserver.public.accounts`

В качестве ключа сообщения используется `account_id`. Это позволяет связывать события с конкретной записью справочника.

Kafka обеспечивает:
- буферизацию поступающих событий;
- разделение источника и потребителя данных;
- возможность повторного чтения сообщений;
- независимое масштабирование компонентов системы.

### Spark Structured Streaming

Spark отвечает за обработку поступающих CDC-событий и формирование исторических записей SCD Type 2.

Для обработки выбран микробатчевый режим. Данные поступают из Kafka и обрабатываются небольшими пакетами с заданным интервалом.

Такой подход удобен для данной задачи, поскольку позволяет использовать SQL-операции и `MERGE` для изменения исторической таблицы.

## 3. Архитектура

Архитектура представлена на схеме `architecture.png`.

Исходный файл схемы — `architecture.drawio`.

Основной поток данных:

**PostgreSQL → Debezium → Kafka → Spark Structured Streaming → Apache Iceberg / MinIO → Trino**

Lakekeeper используется для управления каталогом Iceberg и предоставления REST API для работы с метаданными таблиц.

### Описание компонентов архитектуры

| Компонент | Роль в архитектуре |
|---|---|
| PostgreSQL | Операционная база данных и источник изменений |
| Debezium | Захват изменений через WAL |
| Kafka | Передача и буферизация CDC-событий |
| Spark Structured Streaming | Обработка событий и формирование SCD Type 2 |
| Apache Iceberg | Табличный формат для хранения исторических данных |
| MinIO | Объектное хранилище для файлов данных |
| Lakekeeper | Управление каталогом и метаданными Iceberg |
| Trino | Выполнение аналитических SQL-запросов |

### Почему выбрана такая архитектура

Каждый компонент отвечает за отдельную часть обработки данных.

PostgreSQL остаётся основной операционной системой и не используется аналитиками для тяжёлых исторических запросов.

Debezium получает изменения из журнала транзакций, а Kafka обеспечивает передачу событий между компонентами.

Spark обрабатывает события и формирует историческую таблицу. Apache Iceberg используется для хранения данных в табличном формате, а MinIO — для хранения файлов Parquet.

Lakekeeper управляет метаданными таблиц, а Trino предоставляет SQL-интерфейс для аналитиков.

Такое разделение позволяет независимо развивать и масштабировать отдельные части системы.

## 4. Docker — состав и состояние компонентов

Для развёртывания компонентов подготовлен файл `docker-compose.yml`.

В нём описаны сервисы, необходимые для работы архитектуры: PostgreSQL, Kafka, Debezium, Spark, MinIO, Lakekeeper и Trino.

| Блок | Статус |
|---|---|
| PostgreSQL | Описан в Docker Compose, настроена логическая репликация |
| Kafka | Описан в Docker Compose, предусмотрен режим KRaft |
| Debezium Kafka Connect | Описан в Docker Compose, предусмотрена регистрация PostgreSQL Connector |
| Spark Structured Streaming | Описан в Docker Compose, подготовлено задание обработки CDC |
| MinIO | Описан в Docker Compose, предусмотрено объектное хранилище |
| Lakekeeper | Описан в Docker Compose, предусмотрена инициализация каталога |
| Trino | Описан в Docker Compose, настроен Iceberg REST Catalog |

### Запуск проекта

Для запуска инфраструктуры предусмотрена команда:

```bash
docker compose up -d --build
```

Для просмотра состояния контейнеров:

```bash
docker compose ps -a
```

Для просмотра логов отдельных компонентов:

```bash
docker compose logs --tail=100 postgres
docker compose logs --tail=100 kafka
docker compose logs --tail=100 kafka-connect
docker compose logs --tail=100 spark-job
```

### Особенности развёртывания

Для PostgreSQL настроены параметры логической репликации. Это необходимо для работы Debezium.

Kafka работает в режиме KRaft, поэтому для неё не требуется отдельный ZooKeeper.

Для MinIO предусмотрена отдельная инициализация хранилища. Lakekeeper использует собственную базу PostgreSQL для хранения метаданных.

Spark запускает приложение `scd2_job.py`, которое подключается к Kafka и выполняет обработку событий.

Trino настроен для подключения к Iceberg через REST Catalog Lakekeeper.

Конфигурация инфраструктуры подготовлена в Docker Compose. Фактическое состояние запущенных контейнеров и результаты выполнения проверочных запросов в данном отчёте не фиксировались.

## 5. Описание прохождения данных

В этом разделе рассмотрен полный путь данных от операционной базы PostgreSQL до аналитического слоя.

### Шаг 1. Создание и изменение данных в PostgreSQL

В PostgreSQL создаётся таблица `public.accounts`, содержащая информацию о счетах.

В таблицу добавляются записи, после чего в процессе работы могут выполняться операции INSERT, UPDATE и DELETE.

Например, если у счёта изменяется владелец или статус, PostgreSQL регистрирует соответствующее изменение в WAL.

Таким образом, журнал транзакций становится источником информации для CDC.

### Шаг 2. Захват изменений с помощью Debezium

Debezium подключается к PostgreSQL с использованием логической репликации и плагина `pgoutput`.

Он отслеживает изменения таблицы `public.accounts` и преобразует их в события.

Событие содержит тип операции, временную метку и информацию о записи.

Например, при изменении статуса счёта Debezium формирует событие обновления, содержащее новое состояние записи.

### Шаг 3. Передача событий в Kafka

После формирования CDC-события Debezium отправляет его в Kafka.

Для таблицы `public.accounts` используется топик `dbserver.public.accounts`.

Ключом сообщения выступает идентификатор счёта. Благодаря этому события можно связать с конкретной сущностью.

Kafka выступает промежуточным буфером между источником и обработчиком. Это снижает зависимость компонентов друг от друга и позволяет потребителю читать накопленные события.

### Шаг 4. Обработка данных в Spark Structured Streaming

Spark читает сообщения из Kafka и преобразует JSON-события Debezium в структурированные записи.

Из события извлекаются:
- тип операции;
- идентификатор счёта;
- имя владельца;
- статус;
- баланс;
- временная метка события.

Для обработки используется `foreachBatch`, который позволяет выполнять операции над каждым микробатчем.

Далее данные передаются в логику SCD Type 2.

### Шаг 5. Формирование истории SCD Type 2

Для хранения истории используется подход SCD Type 2.

Его основная идея заключается в том, что при изменении записи старая версия не перезаписывается, а закрывается. После этого создаётся новая версия записи с актуальными значениями.

В таблице истории используются дополнительные поля:

| Поле | Назначение |
|---|---|
| `valid_from` | Дата начала действия версии |
| `valid_to` | Дата окончания действия версии |
| `is_current` | Признак актуальной версии |
| `op` | Тип операции CDC |

Пример того, как может выглядеть история одного счёта:

| account_id | owner_name | status | valid_from | valid_to | is_current |
|---|---|---|---|---|---|
| 1 | Иванов | active | 2026-01-01 | 2026-02-15 | false |
| 1 | Иванов | blocked | 2026-02-15 | NULL | true |

В данном примере у счёта изменился статус. Предыдущая версия получила дату окончания действия, а новая версия стала актуальной.

Такой подход позволяет восстановить состояние справочника на любую дату, для которой сохранена история.

В рамках проекта логика обработки SCD Type 2 реализована в Spark-приложении `scd2_job.py`. Для изменения существующих записей используется операция `MERGE`.

### Шаг 6. Хранение данных в Apache Iceberg и MinIO

После обработки данные записываются в таблицу:

`lake.db.accounts_scd2`

Для хранения используется Apache Iceberg.

Физические файлы таблицы размещаются в MinIO в объектном хранилище. В качестве формата файлов используется Parquet.

Iceberg позволяет работать с большими аналитическими таблицами, управлять метаданными и выполнять операции изменения данных.

MinIO предоставляет S3-совместимый интерфейс, поэтому к нему могут подключаться разные компоненты аналитической инфраструктуры.

### Шаг 7. Управление каталогом через Lakekeeper

Lakekeeper используется в качестве REST Catalog для Apache Iceberg.

Он отвечает за управление метаданными таблиц и предоставляет интерфейс для взаимодействия с каталогом.

Это позволяет Spark и Trino обращаться к одним и тем же таблицам через единый каталог.

### Шаг 8. Аналитика через Trino

На последнем этапе Trino подключается к Iceberg через Lakekeeper.

Аналитики могут выполнять SQL-запросы к таблице `lake.db.accounts_scd2`, не обращаясь напрямую к PostgreSQL.

Например, чтобы получить актуальные записи:

```sql
SELECT *
FROM lake.db.accounts_scd2
WHERE is_current = true;
```

Чтобы получить историю конкретного счёта:

```sql
SELECT *
FROM lake.db.accounts_scd2
WHERE account_id = 1
ORDER BY valid_from;
```

Чтобы получить состояние справочника на определённую дату:

```sql
SELECT account_id, owner_name, status, balance
FROM lake.db.accounts_scd2
WHERE valid_from <= TIMESTAMP '2026-03-01 00:00:00'
  AND (valid_to > TIMESTAMP '2026-03-01 00:00:00'
       OR valid_to IS NULL);
```

Таким образом, аналитический слой предоставляет возможность работать как с текущим состоянием данных, так и с их историческими версиями.

## 6. Выводы

В ходе выполнения практической работы была спроектирована архитектура обработки изменений операционного справочника на основе CDC и SCD Type 2.

Для получения изменений из PostgreSQL выбран Debezium, который использует логическую репликацию и журнал WAL. Для передачи событий применяется Kafka. Обработка данных выполняется с помощью Spark Structured Streaming, а для хранения исторических данных используется Apache Iceberg.

### Почему выбран SCD Type 2

Для данной задачи SCD Type 2 подходит лучше всего, поскольку необходимо сохранять историю изменений.

SCD Type 1 просто перезаписывает старые значения и не позволяет восстановить предыдущее состояние записи.

SCD Type 2 сохраняет предыдущие версии и позволяет выполнять исторические запросы. Это особенно важно для бухгалтерии и аналитики, где необходимо понимать, как менялись данные со временем.

### Почему выбран микробатч

В качестве способа обработки выбран Spark Structured Streaming в микробатчевом режиме.

Он позволяет обрабатывать события небольшими пакетами и использовать возможности Spark SQL, включая `MERGE`.

Для данной задачи микробатч является разумным компромиссом между скоростью обработки и удобством работы с историческими таблицами.

### Что можно улучшить в дальнейшем

В дальнейшем архитектуру можно расширить:
- добавить генератор тестовых данных для проверки нагрузки;
- проверить корректность обработки нескольких изменений одной записи в рамках одного микробатча;
- добавить обработку повторных событий и удалений;
- реализовать дополнительные проверки целостности исторических данных;
- настроить мониторинг Kafka, Spark и других компонентов;
- добавить автоматические тесты для проверки сценариев INSERT, UPDATE и DELETE.

### Итог

В результате получилась архитектура, в которой операционная база данных отделена от аналитического слоя. Изменения фиксируются через CDC, передаются в Kafka, обрабатываются Spark и сохраняются в Iceberg.

Главное преимущество такого решения — возможность хранить историю изменений справочника и выполнять аналитические запросы на основе состояния данных в прошлом, не создавая дополнительную нагрузку на основную PostgreSQL.
